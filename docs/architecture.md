# Error Vault — Architecture

Error Vault is a personal technical knowledge system for capturing, understanding,
and reusing software errors. It is a mobile-first Progressive Web App (PWA) backed
by a REST API and a PostgreSQL database.

## Stack

| Layer      | Technology                                             |
|------------|--------------------------------------------------------|
| Frontend   | React 19, TypeScript, Vite 8, React Router 7, vite-plugin-pwa |
| Backend    | Spring Boot 3.5 (3.5.16), Java 21, Spring Web, Spring Data JPA, Bean Validation |
| Database   | PostgreSQL 16 (local via Docker Compose), Flyway migrations |
| Tests      | Vitest + Testing Library (unit), Playwright (mobile e2e), JUnit 5 + MockMvc (API) |

## System overview

```
 ┌────────────────────────────┐         HTTP/JSON          ┌─────────────────────────┐        JDBC        ┌──────────────┐
 │ Browser / installed PWA    │  ───────────────────────▶  │ Spring Boot REST API    │  ───────────────▶  │ PostgreSQL   │
 │ React + TS (Vite build)    │   /api/* (Vite dev proxy   │ com.errorvault          │                    │ Flyway-owned │
 │ Service worker (offline    │    in development)         │ port 8080               │                    │ schema       │
 │ app shell)                 │  ◀───────────────────────  │ /actuator/health        │  ◀───────────────  │              │
 └────────────────────────────┘                            └─────────────────────────┘                    └──────────────┘
```

- The frontend is a static single-page app. In development, Vite serves it on port
  5173 and proxies `/api` to the backend on port 8080, so there is no CORS setup.
- In production the built `frontend/dist` can be served by any static host, with
  `/api` routed to the backend.

## Backend design

- **Layering:** `controller` (HTTP, validation, DTO mapping) → `service` (business
  rules) → `repository` (Spring Data JPA) → PostgreSQL.
- **Schema ownership:** Flyway migrations in `backend/src/main/resources/db/migration`
  are the only way the schema changes. Hibernate runs with `ddl-auto: validate`.
- **Configuration:** defaults point at the local Docker Compose database; every
  value can be overridden with `SPRING_DATASOURCE_*` / `SERVER_PORT` environment
  variables.
- **Errors:** validation failures return HTTP 400 with field messages; missing
  records return HTTP 404 (both implemented in Phase 2).
- **Health:** `/actuator/health` (liveness and readiness probes enabled).

## Data model (Phase 2 MVP)

Table `error_record` (created by migration `V2__error_record.sql`):

| Column        | Type                          | Notes                                  |
|---------------|-------------------------------|----------------------------------------|
| `id`          | `UUID` primary key            | Generated by the application            |
| `title`       | `VARCHAR(200)` not null       | Short name of the error                 |
| `error_message` | `TEXT` not null             | Exact error text as seen                |
| `stack_trace` | `TEXT` null                   | Optional                                |
| `source`      | `VARCHAR(100)` null           | Language, tool or system (e.g. "Java") |
| `environment` | `VARCHAR(100)` null           | e.g. "local", "staging"                 |
| `root_cause`  | `TEXT` null                   | Your understanding of the cause         |
| `resolution`  | `TEXT` null                   | What fixed it                           |
| `tags`        | `VARCHAR(500)` null           | Comma-separated, normalised to lowercase |
| `created_at`  | `TIMESTAMPTZ` not null        |                                        |
| `updated_at`  | `TIMESTAMPTZ` not null        |                                        |

Indexes: `created_at` (default sort) and a B-tree on `title`. Full-text search is
out of scope for the MVP (see roadmap).

## REST API (Phase 2 MVP)

| Method | Path                  | Purpose                                           |
|--------|-----------------------|---------------------------------------------------|
| GET    | `/api/errors`         | List, newest first. Optional `q` (title/message/tags contains) and `tag`. |
| POST   | `/api/errors`         | Create a record. Returns 201 with the record.     |
| GET    | `/api/errors/{id}`    | Fetch one record. 404 if missing.                 |
| PUT    | `/api/errors/{id}`    | Replace an editable record. 404 if missing.       |
| DELETE | `/api/errors/{id}`    | Delete a record. 204, or 404 if missing.          |
| GET    | `/actuator/health`    | Health probe.                                     |

## Frontend design

- **Mobile first:** base CSS targets 360–430px phones; wider layouts are added with
  `min-width` media queries. Touch targets are at least 44px. No horizontal scrolling.
- **Routing:** React Router. Routes: `/` (list), `/errors/new`, `/errors/:id`,
  `/errors/:id/edit`. Unknown paths show a not-found page.
- **Data access:** a small typed `fetch` wrapper in `src/api/` calling `/api/*`.
- **PWA:** `vite-plugin-pwa` generates a web manifest and a Workbox service worker
  that precaches the app shell, so the app opens offline. Record data is fetched
  from the API and is not cached offline in the MVP.
- **Theming:** CSS custom properties with light and dark palettes
  (`prefers-color-scheme`, plus `data-theme` override).

## Non-functional requirements (MVP)

- Single user, no authentication yet. Authentication is a later phase and is
  explicitly out of MVP scope.
- Input limits enforced server-side (title ≤ 200 characters, tags ≤ 500).
- Secrets are never committed; database credentials come from environment variables.
